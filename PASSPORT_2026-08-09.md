# ЭРА — паспорт текущего состояния

Дата: 2026-08-09

Статус: рабочий прототип собственного AI-интерфейса.

Этот документ является новым паспортом проекта и не заменяет предыдущий паспорт с экспериментами Android Assistant / Keyguard / ChatGPT Voice.

---

# 1. Цель проекта

Эра — персональная AI-среда, в которой Сфера является постоянным интерфейсом между пользователем, моделями ИИ, памятью, программами и устройствами.

Базовая схема:

пользователь
↓
Сфера
↓
модель ИИ
↓
контролируемый слой инструментов
↓
приложения / ОС / файлы / устройства
↓
результат

Долгосрочная цель:

Сфера не должна быть привязана:

- к конкретной модели;
- к OpenAI;
- к конкретному Android-смартфону;
- к официальному приложению ChatGPT;
- к одной операционной системе.

Модель должна рассматриваться как сменный вычислительный движок.

# 5. OpenAI API

Создан:

`OpenAiClient.kt`

Используется:

`POST /v1/responses`

API-ключ не записан непосредственно в исходный код.

Пользователь выбирает внешний текстовый файл с API-ключом через Android file picker.

Приложение сохраняет URI файла и получает ключ через `ContentResolver`.

Это позволяет не хранить секретный API-ключ внутри GitHub-репозитория.

# 6. Продолжение разговора

`OpenAiClient` сохраняет:

`previousResponseId`

После каждого успешного ответа сохраняется новый `response.id`.

Следующий запрос передаёт:

`previous_response_id`

Таким образом OpenAI может продолжать текущую цепочку разговора без ручной передачи всей истории чата приложением.

Также существует:

`resetConversation()`

для сброса текущей API-цепочки.

Важно:

текущий механизм является временным способом сохранения контекста разговора.

В будущем история и долговременная память Сферы должны принадлежать самой Эре, а не конкретному провайдеру модели.

---

# 7. Инструкции Сферы

В меню приложения создан раздел:

`Инструкции`

Пользователь может вводить и сохранять собственные инструкции Сферы.

Они хранятся локально через `SharedPreferences`.

При каждом запросе инструкции передаются в OpenAI Responses API через поле:

`instructions`

Это первый прототип переносимого характера / поведения Сферы.

В будущем инструкции должны стать частью отдельного слоя идентичности Сферы вместе с памятью и другими настройками.

# 9. Usage API

Из ответа OpenAI теперь извлекаются реальные данные использования.

Создан:

`OpenAiResponse`

Он содержит:

- `text`;
- `model`;
- `inputTokens`;
- `outputTokens`;
- `cachedTokens`;
- `totalTokens`.

Данные берутся непосредственно из ответа Responses API.

Подтверждено физическим тестированием:

- input tokens приходят;
- output tokens приходят;
- total tokens приходят;
- cached tokens приходят;
- фактически использованная модель определяется.

---

# 10. Prompt Cache

Подтверждена работа кэшированных входных токенов.

Из:

`usage.input_tokens_details.cached_tokens`

Эра получает количество токенов, обработанных через prompt cache.

Тест показал ненулевое количество cached tokens.

Важно:

`input_tokens` уже включает `cached_tokens`.

Поэтому при расчёте стоимости:

обычные входные токены =
input_tokens - cached_tokens

После этого обычные и кэшированные входные токены считаются по разным тарифам.

---

# 11. Расчёт стоимости

Создан:

`UsageCalculator.kt`

Он принимает:

- модель;
- input tokens;
- cached tokens;
- output tokens.

И рассчитывает:

- стоимость обычного входа;
- стоимость кэшированного входа;
- стоимость выхода;
- общую стоимость запроса.

Логика:

обычный input
+
cached input
+
output
=
стоимость запроса

Цены моделей в настоящий момент заданы внутри приложения.

Важно:

цены API являются внешними изменяемыми данными.

Следовательно, в будущем желательно отделить таблицу тарифов от основной логики приложения и предусмотреть простой механизм её обновления.

# 12. Экран «Использование»

Создан отдельный экран:

`UsageActivity`

и layout:

`activity_usage.xml`

Экран содержит несколько блоков.

## Расчётный баланс

Пользователь вручную вводит текущий доступный API-баланс.

Эра хранит:

`initial_balance`

После каждого рассчитанного запроса стоимость добавляется в:

`total_spent`

Расчётный остаток:

initial_balance - total_spent

Таким образом приложение может локально оценивать оставшийся API-баланс.

Это расчётное значение, а не прямое получение реального баланса аккаунта OpenAI.

---

## Текущая сессия

Отображаются:

- отправленные токены;
- кэшированные токены;
- полученные токены;
- стоимость сессии;
- текущая модель.

Для хранения используются:

`KEY_SESSION_INPUT_TOKENS`

`KEY_SESSION_OUTPUT_TOKENS`

`KEY_SESSION_CACHED_TOKENS`

`KEY_SESSION_TOTAL_TOKENS`

`KEY_SESSION_MODEL`

`KEY_SESSION_COST`

Это позволит видеть распределение расходов между моделями.

# 15. Новый архитектурный принцип

Следующий фундаментальный шаг:

отделить Сферу от конкретной модели.

Сейчас:

интерфейс
↓
OpenAiClient
↓
OpenAI

Желаемая архитектура:

интерфейс Эры
↓
единый интерфейс модели
↓
┌ облачная модель
├ локальная модель
└ будущие модели

То есть интерфейс приложения не должен знать, кто именно генерирует ответ.

Для него должно существовать условное действие:

`sendMessage()`

А за ним уже может находиться:

- OpenAI;
- локальная LLM;
- другой облачный провайдер;
- собственный сервер;
- будущая модель.

# 16. Локальная модель

Локальная модель пока НЕ подключена.

Следующий разумный эксперимент:

сначала создать универсальный слой взаимодействия с моделями.

После этого:

1. существующий OpenAI-клиент подключить к этому слою;
2. установить / запустить подходящую локальную модель;
3. подключить её как второй AI-движок;
4. проверить переключение между облачной и локальной моделью без изменения интерфейса чата.

Цель эксперимента:

Сфера должна продолжать работать независимо от того, где физически выполняется модель.

- позволять обновлять устаревшие сведения;
- позволять удалять сведения;
- находить воспоминания естественным языком.

# 18. Переносимость

Один из основных архитектурных критериев проекта:

Эра должна переживать смену телефона.

Переход на другое Android-устройство не должен означать создание нового ассистента с нуля.

Переносимыми должны стать:

- инструкции Сферы;
- настройки;
- память;
- история;
- конфигурация моделей;
- пользовательские данные;
- разрешения, где это возможно;
- резервные копии.

Специфичные для конкретного телефона механизмы должны находиться отдельно от ядра.
